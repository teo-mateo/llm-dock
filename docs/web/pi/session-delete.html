Deleting an ended pi session from the web

Same contract and behaviour as the phone's swipe-to-delete (docs/plans/pi-session-swipe-delete.md): only ended sessions offer it, the row leaves at once, the DELETE waits out a 3-second undo window, a failure puts the row back and says why. Builds on the project tree (session-tree.html).

TWO ENTRY POINTS
  1. List row: on hover or keyboard focus of an ended row, the status word is replaced by a 24px trash button (aria-label="Delete session <name>"). It turns red on hover. Clicking it must not open the session.
  2. Session header: a quiet red-outline Delete button, shown only when the open session has ended.
NOT OFFERED
  • Live sessions get no control at all — the server answers 409 for them, and ending a session is Stop's job.
  • No confirm dialog: the undo window is the safety net.
  • Deleting a parent deletes only that row; its subagents move up and show as roots.

FLOW
  1. Click: the row leaves the list at once (its project count drops; an emptied project disappears). If it was open, navigate to /pi.
  2. A toast at the bottom of the list column: Deleted <name> · Undo, with a thin bar draining over 3 s. Undo restores the row; nothing was sent.
  3. When the window expires, send DELETE /api/pi/sessions/<sid>/<iid>. 200 or 404 → done, silently.
  4. 409 (pi reconnected meanwhile): row comes back, toast A running session can't be deleted.
  5. Any other failure: row comes back, toast names the session and the error. Never show the raw code (pi_session_live).
  6. A second delete during the window commits the first one immediately — one pending delete at a time, like the phone.
  7. A stream update during the window must not bring the pending row back.
ALSO
  • The sessions stream already sends session_removed; the web ignores it today, so a session deleted from the phone stays on the web until reload. Apply it: drop the row, and if it is the open session show the existing no longer known state.
