Design proposal · v0 · signed off, superseded on specifics

llm-dock, in your pocket

A plain chat client for Android that talks to the dashboard's existing API. Conversations live on the server, not on the phone — the same threads you see at :3399/v2. Two tabs: chats, and a read-and-switch view of the rig itself. No critic, no sidekick, no configuration. Sixteen screens below. The keep/cut decisions have since been taken — see the note under the legend.

Auth password or TOTP → 8 h session Storage server-side chat.db Streaming SSE, reattachable Nothing new server-side — every screen maps to an endpoint that exists today
core the app is pointless without it your call works today, costs effort — keep or cut proposed cut exists in v2, left out here corrected this page was wrong; see the note

Status: validated design, superseded on specifics. These screens were reviewed and signed off, and remain the reference for layout and visual language. The requirements now live in android/docs/Plan_TOC.md — scope, ground rules, the endpoint surface, and one file per feature with acceptance criteria. Where this page and the requirements disagree, the requirements win.

Corrections are marked corrected inline below. In short: the login endpoint named on screen 01 was wrong; Stop does not keep partial text (screen 04); the conversation list carries no message preview (02); and the GPU API exposes no per-container VRAM or true uptime (10a).

Decisions taken since sign-off: no projects on the phone at all, follow the system theme, bottom navigation, stopping a container is always allowed, no maths rendering in v1, and no notifications — screen 08b's headline feature needs server code that does not exist, so it is cut rather than deferred, along with search, the tok/s readout and the offline cache. Full register with reasons: android/docs/Dropped-Features.md.

01

Getting in

The dashboard already accepts a TOTP code and hands back an 8-hour sliding session token. The phone does the same and keeps the token in the Android Keystore, so you type six digits roughly once a day.

On this screen

  • coreServer address. Typed once, remembered. Needed because the same app should work on LAN and over the proxy.
  • coreSix-digit TOTP. Sent as X-TOTP-Code; the reply carries a totp-… bearer token good for 8 h, extended on every request.
  • your callRaw API token entry. Handy on a device you trust, one less screen to hit. Slightly worse if the phone is lost.
  • your callBiometric unlock in front of the stored token. Not drawn — say the word and it becomes a fingerprint prompt on launch.

corrected The endpoint named here was wrong. POST /api/totp/verify is TOTP enrollment — it requires an already-valid token and writes the secret to config, so it cannot be used to sign in. The two real ways in, both returning an 8 h sliding session: POST /api/auth/session with the password as a bearer (what the login page calls a password is DASHBOARD_TOKEN), or POST /api/auth/login with an X-TOTP-Code header. Still nothing to build server-side.

02

Your conversations

One list, newest first. Threads started on the desktop show up here and vice versa — it's the same chat.db. A thread that is still generating on the server gets a live dot, which is the one thing a phone client can do that the browser tab can't: walk away and come back.

On this screen

  • coreFlat, newest-first list with title, model chip and time. GET /api/chat/conversations, paged.
  • correctedNo last-line preview, though the frame draws one. The list endpoint returns conversation rows without messages, so a preview would cost one extra request per visible row.
  • coreModel chip per thread — colour-coded the way the dashboard badges engines: blue vLLM, grey llama.cpp, amber ds4, purple OpenRouter. Tells you what a thread costs before you open it.
  • coreLive "generating" dot. Any thread with an active run. Tap it to reattach mid-stream — see screen 08.
  • your callProject groups. Collapsible headers, same grouping as the sidebar. Cutting them makes this a single flat list; threads in projects still appear, just unsorted.
  • your callSwipe to delete and long-press multi-select. POST /api/chat/conversations/delete takes a batch.
  • your callSearch. The API has no search endpoint — this would filter titles client-side over the loaded page unless you want one added.
  • coreThe bottom bar. Chats and Models — the second tab is screen 10. It appears only on the two list screens; open a thread and it gets out of the way.
  • cutSpin-off threads. A desktop reading gesture; the taskbar of floating windows has no phone equivalent. Spin-offs made on the desktop still open here as normal threads.
03

Starting one

A sheet, not a screen — three lines you can ignore. Everything is prefilled from your last chat, so the fast path is tap New chat, tap Start, type.

On this screen

  • coreModel. The only required field — main_service on POST /api/chat/conversations.
  • your callSystem prompt picker. Your managed prompts from /api/chat/prompts. Cutting it means every phone thread uses the server default, which you can still edit from the dashboard.
  • your callTools. Which MCP servers this thread may call. See screen 07.
  • your callProject. Only meaningful if you keep project grouping. It also decides whether the model gets the file tools.
  • cutCritic / sidekick model. Gone, as asked. Threads created on the phone send sidekick_service: null; critiques you ran on the desktop simply don't render here.

The stripped-down version of this sheet is one row — Model — and a Start button. Say so and I'll cut the other three.

04

The thread, mid-answer

The heart of it. Your message in mono, the model's in serif — the same split the dashboard uses, and it earns its keep on a small screen: you can tell who's talking without looking for an avatar. Reasoning and tool calls collapse to one line each so they never bury the answer.

On this screen

  • coreToken-by-token streaming over the run's SSE stream, with the model name pinned under the title so you always know who's answering.
  • coreStop. Cooperative cancel. Prefer POST /api/chat/conversations/<id>/cancel-active-run with expected_run_id — the server can always find a conversation's active run, and the guard stops a stale tap killing a newer one.
  • correctedPartial text is NOT kept. A cancelled run marks itself cancelled and saves no assistant message — what's on screen is client-side only and vanishes on refetch. A failed run is the opposite: it persists its partial plus the error. Don't treat the two alike.
  • your callLive tok/s readout in the stop bar. You care about this number on the desktop; it costs nothing to compute here.
  • your callCollapsed reasoning block. Tap to expand. Cutting it means thinking output is dropped silently on the phone.
  • your callTool-call cards. Name, arguments, result, expandable. Only matters if you keep MCP tools on mobile at all.
  • cutCritique overlay — the yellow annotated spans. No sidekick, no overlay.

Leaving the screen does not stop the run. The server keeps generating and persists the reply; the app just unsubscribes. That's already how ChatRunner behaves — it's what makes the phone client pleasant.

05

What the model can put on screen

Markdown, code with a copy button, tables, math, and images returned by tools. Every one of these already comes down the same stream — the question is how much of the renderer is worth writing for a 6-inch screen.

On this screen

  • coreMarkdown + fenced code with a language label and a copy button. Non-negotiable for how you use these models.
  • coreCopy / select / share under each answer. Share hands the text to any other Android app.
  • your callTables. They scroll sideways inside their own box. Cheap to keep, ugly to cut.
  • your callKaTeX math. Real cost on Android — either a WebView per formula or a maths renderer. Worth it only if you actually ask these models for maths on the phone.
  • your callTool images — Schemdraw circuits, rendered HTML artifacts. Circuits are a picture and work fine; HTML artifacts need a WebView.
  • your callSerif for answers, mono for your own text. A borrow from the dashboard. Some people hate serif on phones — settings has a toggle.
06

Writing, and fixing what you wrote

Two states of the same bar. The composer grows to about five lines and then scrolls; long-press on your own message opens the edit path, which truncates the thread from that point and re-runs — the same destructive-but-useful behaviour as the desktop.

On these screens

  • coreMulti-line composer with send. Enter inserts a newline; the button sends — the opposite of the desktop, because thumbs.
  • coreLong-press menu — copy, select, share, delete. DELETE …/messages/<id> already exists and refuses while a run is active.
  • your callEdit and resend. PUT …/messages/<id> truncates from that turn and re-runs. Powerful, and easy to fat-finger on a phone — it gets a confirm.
  • your callImage attachments from camera or gallery. The API takes them; on a phone this is the single most natural input you have — a photo of a screen, a whiteboard, an error.
  • your callVoice input. Drawn as a mic. Android's own dictation is free; a Whisper round-trip to the server is not, and there's no endpoint for it today.
07

Picking a model, picking tools

The model list is what is running right now, straight from the dashboard. Stopped containers are shown greyed so you know why your favourite isn't there — whether the phone may start one is a real decision, not a UI detail.

On these screens

  • coreRunning models, grouped by engine with port and VRAM. Straight from the services API the dashboard already polls.
  • coreSwitch model mid-thread — same list, reached from the ⋮ menu. The next turn goes to the new model.
  • your callOpenRouter models. Keep them and the phone works when the rig is off or busy; cut them and the app is purely local.
  • your callStart a stopped container from the phone. Genuinely useful — and one mistap swaps 60 GB of VRAM out from under whatever is running. If you keep it, it gets a confirm and it is the only dashboard control in the app.
  • your callPer-chat tool toggles. If tools are always the same set for you, this becomes one line in settings instead of a sheet.
08

Coming back to it

The mobile-specific case, and the reason this is worth building rather than bookmarking /v2. Runs live on the server: lock the phone mid-answer, lose signal on the train, come back — the reply finished without you and the app catches up from the replay buffer.

On these screens

  • coreReattach on open. If the thread has an active run, resubscribe to its stream and replay what you missed. GET /api/chat/runs/<id>/stream does this today.
  • coreHonest offline state. Retry with backoff, keep the draft, never silently lose a message.
  • your callNotification when an answer lands while the app is closed. This is the killer feature and the biggest single build item — a foreground service polling, or a small push endpoint on the dashboard. Nothing exists server-side today.
  • your callFailure notifications — a run that dies because a container fell over. Same machinery as above, near-zero extra cost once it exists.
  • your callRead threads offline. Cache the last N conversations so a dead link still shows you yesterday's answer. Sending obviously still needs the server.

Be blunt with me about the notification. Everything else here is a client over an API that already exists. That one needs a small amount of new server code, and it's the difference between an app and a bookmark.

09

Settings

Short on purpose. Anything that belongs to the server — the default system prompt, the OpenRouter list, MCP registry — stays on the dashboard; the phone only holds what's about this phone.

On this screen

  • coreServer + session state and a sign-out that actually clears the token.
  • coreText size. The one accessibility knob that matters when you read model output on a phone in bed.
  • your callDefaults for new chats. Only needed if the new-chat sheet keeps more than the model row.
  • your callKeep screen on while generating. Nice for watching a long answer; costs battery.
  • cutEditing the server's default system prompt, the OpenRouter list, the MCP registry. All dashboard territory. The phone reads them, never writes them.
  • cutGPU monitor, container start/stop, benchmarks, project file editing. This is a chat app.
10

The rig

A second tab: see what's loaded, start and stop it, read the logs. Deliberately not a dashboard — there is no way to create a service, edit flags, change ports or rotate keys from the phone. You can only turn on what already exists and watch it come up.

On these screens

  • coreLive GPU header. One card: VRAM used of 96 GB, plus util, temp and watts. GET /api/gpu/stream pushes it.
  • correctedThe per-container VRAM split isn't available. nvidia-smi is queried for device totals only — no per-process breakdown reaches the API, and the sole per-service number is weights-on-disk size, not resident VRAM. Draw one total bar, or label the segments as estimates; never present them as measured.
  • coreRunning / stopped split with port and model size. GET /api/services for the snapshot, /api/services/stream to keep it live without polling.
  • correctedUptime is really "created ago". The payload carries the container's creation time, not its last start, so the figure is wrong for anything that has been restarted.
  • coreStart and stop from the row or the detail screen — POST /api/services/<name>/start|stop. Restart is stop-then-start, same as the dashboard.
  • coreStreaming logs with level colouring and follow-tail. GET /api/services/<name>/logs/stream, already SSE. Share hands the buffer to any app — useful for pasting a startup failure somewhere.
  • coreVRAM guard before starting. Everything shares one GPU, so a start that doesn't fit is the app's one genuinely dangerous action. It names what is running, what stopping frees, and warns that in-flight chats die. Stop both, then start is a compound action the phone performs for you.
  • your callRead-only flags on the detail screen — the rendered CLI from GET /api/services/<name>. Useful when you're deciding whether to start something; cut it and the detail screen is status plus logs.
  • your call"New chat" straight from a model. Opens the chat tab with that service preselected. Cheap, and it's how you'd actually use this tab.
  • your callReadiness watching. vLLM takes 1–3 min to come up. The app can watch for Uvicorn running / HTTP server is listening and notify you when the model is actually usable, instead of you re-opening the logs.
  • cutEverything configuration. No create, no flag editing, no port or key changes, no delete, no compose rebuild. The phone starts, stops and observes — nothing that can corrupt services.json from a bad tap.
  • cutBenchmarks. Running llama-bench from a phone helps nobody.

This tab is why the app gets a bottom bar. Two tabs, Chats and Models — see screen 02. The alternative is no nav bar at all and a small GPU chip in the chat list's app bar that opens Models as a pushed screen; that keeps the app feeling like one thing. Tell me which you prefer.

Open questions

  1. Notifications. Worth a small server change, or do you only ever chat with the app open?
  2. Stopping a model that a chat is mid-answer on. Screen 10d warns you. Should it also refuse — or is a warning enough on a single-user rig?
  3. Bottom bar, or Models as a pushed screen off the chat list? Two tabs is the discoverable answer; one screen is the honest one if you'll open Models once a week.
  4. Dark only, or follow the system theme? The mockups commit to dark, matching the dashboard. A light theme is a second palette to maintain.
  5. How the app gets built. Native Kotlin/Compose, or a thin wrapper — the answer changes what's cheap. KaTeX and HTML artifacts, for instance, are nearly free in a WebView and expensive natively.
  6. Does the phone ever need to see projects at all, or is that purely desktop work?
